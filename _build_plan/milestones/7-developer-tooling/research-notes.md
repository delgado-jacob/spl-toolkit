## Primary protocol sources

1. [OASIS SARIF 2.1.0 plus approved Errata 01](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html), approved errata dated 2023-08-28; consulted 2026-09-07. Sections 3.4, 3.14.27, 3.20.14 and 3.30 establish URI location rules, explicit column measurement, invocation success, and source regions. These are exporter choices conforming to the standard, not a claim every consumer accepts every SARIF feature.
2. [Official SARIF schema with errata](https://docs.oasis-open.org/sarif/sarif/v2.1.0/errata01/os/schemas/sarif-schema-2.1.0.json). 3. [Microsoft LSP specification](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/) and [official project homepage](https://microsoft.github.io/language-server-protocol/), consulted 2026-09-07. The homepage advertises 3.18; M7 deliberately selects the established 3.17 contract for its limited feature surface, with no latest-version/full-protocol claim.
4. [Official LSP 3.17 position definition](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/types/position.md): zero-based line/character, negotiated encoding, mandatory UTF-16 support. Convert from engine byte offsets using exact text, never subtract one from a Unicode column and call it UTF-16.
5. [Official didChange definition](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/textDocument/didChange.md): changes are ordered and the version names the resulting document. 6. 7. [Official documentHighlight definition](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/language/documentHighlight.md): highlights can carry Read/Write/Text kinds. M7 will use proven canonical binding/origin relationships; it will not highlight same-spelled fields across unrelated scopes as one symbol.
8. [Official initialize definition](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/general/initialize.md): initialization ordering and advertised capabilities constrain subsequent traffic. Only implemented features are advertised.

## Cancellation qualification

[Official LSP 3.17 base specification source](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/specification.md), consulted 2026-09-07, requires a response even to a cancelled request. `RequestCancelled` applies when client cancellation is detected; ordinary queued document edits alone do not justify `ContentModified`. That distinction matters: discard stale asynchronous diagnostic publication, but capture a position-based request's source snapshot in message order and complete its response. Internal configuration invalidation may justify `ContentModified`. Cancellation cannot be described as forcibly interrupting ANTLR unless the eventual core provides that verified capability.

### Unix implementation candidate

Acquire and retain the declared root directory, then split each already validated relative selection into individual child names. Open intermediate names with `Openat(parentFD, component, O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC, 0)`. Never submit an untrusted multi-component path to a final-component-only flag. Open the leaf read-only with `O_NOFOLLOW|O_CLOEXEC|O_NONBLOCK|O_NOCTTY`, inspect the acquired descriptor with File.Stat and require a regular file, then read that same descriptor. O_NONBLOCK avoids waiting for a substituted FIFO; O_NOCTTY avoids acquiring a controlling terminal. Neither constitutes a promise that arbitrary privileged device nodes can be safely opened. No path-based restat or reopen may become the authority for what is read. [POSIX open/openat](https://pubs.opengroup.org/onlinepubs/9799919799/functions/open.html), [pinned Linux wrapper](https://raw.githubusercontent.com/golang/sys/v0.20.0/unix/syscall_linux.go).

For directory discovery, wrap the owned descriptor with `os.NewFile` and use **Readdirnames**, then sort and reacquire children relative to the retained parent. Do not authorize traversal from DirEntry.Info or File.Readdir metadata: Go1.22 implementations can restat `f.name + "/" + child`. Read-only inspection of the installed floor-toolchain files `src/os/dir_unix.go`, `src/os/dir_darwin.go` and `src/internal/poll/fd_opendir_darwin.go` under `/private/tmp/spl-toolkit-floor-tools/gomodcache/golang.org/toolchain@v0.0.1-go1.22.12.darwin-arm64` confirms that the name-only branch avoids these restats and Darwin duplicates the existing FD for fdopendir. Go's [directory source](https://go.dev/src/os/dir_darwin.go) is primary provenance but is current, not the inspected floor version. Let os.File own close after wrapping; do not independently close the same descriptor. Resource lifetime and Go1.22 behavior require actual tests later.

Avoid implementing Darwin enumeration with x/sys ReadDirent/Getdirentries: the [pinned Darwin source](https://raw.githubusercontent.com/golang/sys/v0.20.0/unix/syscall_darwin.go) explicitly documents a skip-count simulation with limitations under directory edits and quadratic restarting. The standard library already has a descriptor-based alternative. Directory mutation still does not become an atomic snapshot; retain discovered entries whose acquisition later fails and report enumeration errors rather than falsely certify a complete corpus.

Linux [openat2](https://man7.org/linux/man-pages/man2/openat2.2.html) offers stronger whole-path resolution flags on newer kernels, including no-symlink and beneath-root checks. It is unnecessary for the minimum shared single-component strategy and has no Darwin counterpart. Do not introduce an optional Linux-only containment contract or require mount refusal implicitly.

### Windows implementation candidate

Exact [v0.20.0 syscall wrappers](https://raw.githubusercontent.com/golang/sys/v0.20.0/windows/syscall_windows.go) and [types/constants](https://raw.githubusercontent.com/golang/sys/v0.20.0/windows/types_windows.go) supply all calls in the table. They do not supply NtQueryDirectoryFile or FILE_FULL_DIR_INFO / FILE_ATTRIBUTE_TAG_INFO Go structs. Use the existing GetFileInformationByHandleEx wrapper with minimal local ABI layouts rather than add another syscall binding or upgrade the module; verify size/offset/alignment in future Windows tests.

For each validated single component, set `OBJECT_ATTRIBUTES.RootDirectory` to the retained parent handle. Use `NtCreateFile` with `FILE_OPEN`, synchronous non-alert I/O and SYNCHRONIZE access; request directory access/FILE_DIRECTORY_FILE for intermediate components and read access/FILE_NON_DIRECTORY_FILE for the leaf. Hold handles through acquisition and read from the checked handle. This is the documented [user-mode NtCreateFile interface](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile), not a driver or privilege requirement. Reject absolute/device namespace paths, separators inside components, dot/dot-dot, NUL and colon stream syntax; retain the manifest's prior structural path validation.

`OBJ_DONT_REPARSE` requests failure if parsing encounters a reparse point. `FILE_OPEN_REPARSE_POINT` instead permits opening the reparse object itself, so it must never be treated as proof of an ordinary file. Apply both controls and reject an acquired object's FILE_ATTRIBUTE_REPARSE_POINT; metadata failure also fails closed. Require GetFileType to report FILE_TYPE_DISK and reject directories for leaves. FILE_NON_DIRECTORY_FILE alone also permits devices/volumes. [OBJECT_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes), [attribute/tag information](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_attribute_tag_info), [GetFileType](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfiletype).

Enumerate the held directory with `GetFileInformationByHandleEx(FileFullDirectoryRestartInfo)` followed by FileFullDirectoryInfo calls. Bound and validate each returned record's offsets, byte lengths and UTF-16 filename before treating it as a candidate. Microsoft requires 8-byte record alignment. Reacquire each child relative to the parent; do not substitute pathname-based FindFirstFile or trust enumeration metadata for admission. Unsupported API/filesystem behavior is an acquisition error, not a reason to retry through weaker path calls. [Enumeration API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex), [FILE_FULL_DIR_INFO layout and Windows8/Server2012 floor](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_full_dir_info).

Recommend allowing read/write sharing but omitting FILE_SHARE_DELETE on retained root/ancestor handles. Microsoft documents sharing checks against DELETE access, which is needed for rename. The resulting rename exclusion is an inference from those documented access rules and must be exercised on Windows; conflicting already-open handles can cause acquisition failure and must not trigger a path fallback. [CreateFile sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [rename access requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information).

### Boundary precision and future deterministic tests

Root approved this bounded clarification on 2026-09-08: confinement begins at the **declared root directory object actually acquired**. The final root component must itself be a real directory opened without following a symlink/reparse point. Ordinary OS resolution of ancestors above that declared root is allowed, including macOS aliases such as /tmp. Descendants use single-component descriptor/handle-relative no-follow/no-reparse acquisition with retained root/traversal identities. Fail any acquisition whose safety cannot be established. No trusted volume/filesystem-anchor walk is required. Root also approved withholding Windows FILE_SHARE_DELETE when scoped to acquisition and compatible with required access/error handling, and prefers the already summed x/sys v0.20.0 when it covers these APIs. The approved design/draft files remain unchanged by this research pass.

On Unix, an opened directory descriptor continues to denote the acquired object after rename; a component can move outside its old pathname ancestry while held. On Windows, retained non-delete-sharing handles can prevent such moves. Do not promise identical rename behavior or an immutable directory/content snapshot across platforms. Hard links, mount/bind mounts and a writer changing ordinary file contents are not excluded by the no-symlink guarantee; hash exactly the bytes actually read. Go's [root implementation discussion](https://go.dev/blog/osroot) explicitly separates traversal resistance from mount confinement and describes held-object rename behavior. Any stronger instantaneous-path containment requirement would exceed this candidate's guarantee and must be surfaced rather than inferred from lexical checks.

Future tests should use private synchronization barriers around the narrow OS acquisition calls, with a real temporary filesystem and real open calls; deterministic scheduling must not replace the operation with a success mock. No sleeps or probabilistic race loops are necessary:

1. Pause after discovery/structural validation, replace an unacquired directory component with a symlink or Windows junction to an external sentinel, then resume. Assert failure or discovery exclusion according to the approved entry contract, and that no sentinel bytes enter any report/hash.
2. Pause after acquiring an intermediate directory, rename/replace its pathname and continue through the retained handle. Unix may read the original acquired directory's child or fail; it must never follow the replacement symlink. Separately move the held original directory outside the root to document object-identity behavior rather than silently claim immutable ancestry. On Windows assert rename denial while retained handles are open, or explicit acquisition failure if conflicting DELETE access already existed.
3. Pause before leaf open, replace the leaf with a symlink/reparse object, FIFO or directory, then resume. Assert explicit-file failure and no FIFO hang. Pause after a regular leaf is acquired, replace its pathname and verify any successful bytes come from the acquired handle, not the replacement. Do not promise protection against writes to that same open file.
4. Replace/rename the root pathname after acquisition, then verify use of its held object or explicit platform failure; test a root that is itself a symlink/reparse object separately from an ancestor alias. Test directory enumeration using the held object after pathname replacement, and missing/unreadable children as retained per-document failures.
5. Verify handle/FD closure on every branch, reserved/device/stream path rejection, fixed exclusions, unsupported-platform refusal and Windows ABI parsing bounds. Windows symbolic-link creation can require developer mode/privilege, so record inability to create that fixture as an unrun gate; use a real directory-junction case where available without treating it as proof of every reparse type.

No listed test, Go floor compile, native Windows/Linux check or platform matrix was executed here. Final acceptance needs native component-swap evidence on Linux, Windows and both shipped Darwin architectures (or an explicitly accepted architecture-specific evidence limit), alongside compile/API checks. A macOS host source read and a cross-compile alone cannot close the other OS runtime gates. No remote dispatch, dependency installation or new release pin was authorized by this preflight.

### Smallest viable checked-handle approach

1. Finish input acquisition/report serialization before opening the report destination for mutation. Keep an operation-local protection set of trusted identity snapshots for all acquired query, manifest, rule and target objects, including both impact sides and any local target resource files actually consumed. Inline documents have no filesystem object. Capture identity from the same handle used to read, then close that input handle after acquisition; retain required traversal anchors only within their acquisition scope. Acquisition/read/UTF-8 failure after successful identification does not remove its snapshot from protection. Do not retain one open handle per corpus file through analysis/output. On filesystems with stable live-object IDs, reuse after deletion can conservatively reject an unrelated output, but does not authorize writing the deleted object. If ID support/stability is not trustworthy, classify identity as unresolved rather than assume a snapshot suffices. A loader retaining only text/source hashes needs narrow identity/path-acquisition metadata at final reconciliation, not a new resource framework.
2. Acquire and verify the report destination's explicitly selected existing parent directory through ordinary OS resolution, including its symlink aliases such as macOS /tmp, then retain that directory object. Open/create only the validated output basename relative to the held parent without following a final leaf symlink/reparse point. Output may be outside the corpus root; this provides no additional pathname containment promise. Perform the same protected input identity/location checks and retain the checked output parent/handle through the relevant operation. Reject a final symlink/reparse point or nonregular destination, rather than following it even when its target appears unrelated. Root approved this output-parent distinction on 2026-09-08; the stricter no-follow/no-reparse rule for the final component of a declared input corpus root remains unchanged.
3. For an existing destination, **open without create, truncate, append, overwrite or supersede**, verify regular-file type and retrieve its actual identity, then compare with every protected input snapshot. Any match, unresolved existing/possibly-existing selected input identity or failed destination identity/type check aborts with exit2 before truncation/write. Unix uses Openat with O_WRONLY, O_NOFOLLOW, O_CLOEXEC, O_NONBLOCK and O_NOCTTY; the last two avoid FIFO blocking/controlling-terminal effects, not arbitrary device-open side effects. Windows uses the existing NtCreateFile wrapper, RootDirectory plus one component, FILE_OPEN, required write/read-attributes/synchronize rights, no-reparse controls and the same acquired-object checks from the acquisition note.
4. If and only if the destination open reports trustworthy final-entry absence, use exclusive creation relative to the same retained parent: Unix O_CREAT|O_EXCL with no-follow flags and ordinary new-output permissions, or Windows NtCreateFile FILE_CREATE. Before creation, rule out protected input/manifest/rule/target path-location collisions as described below. If another process wins that creation race, fail; do not reopen-and-truncate the new occupant or repeatedly retry path operations. Do not use Windows FILE_OPEN_IF/FILE_OVERWRITE[_IF]/FILE_SUPERSEDE. Check the newly acquired handle's type/identity too before writing. The operating-system existence check and creation are one operation. [Go exclusive-create flags](https://pkg.go.dev/os#pkg-constants), [NtCreateFile dispositions](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile).
5. Once the checked destination is proved distinct, truncate and write **that same open object**. File.Truncate(0), an explicit offset0 write/seek and checked writes avoid any pathname reopen; propagate truncate/write/close errors as exit2. Truncate does not reset the offset. Do not write a temporary file followed by Rename/ReplaceFile onto a name checked earlier: that adds a pathname race and can replace an input link. Do not attempt error cleanup by removing a path that may now name a replacement object. Close every retained handle on success/failure, with ownership assigned exactly once. [Go File.Truncate/Write](https://pkg.go.dev/os#File.Truncate), [Windows handle-based SetEndOfFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setendoffile).

### Identity details and limits

On Linux/macOS, saved `File.Stat()` results from acquired input descriptors compared with the checked output descriptor's File.Stat result using `os.SameFile` compare device/inode identity and catch hard-link aliases, different path spellings and case aliases where applicable. Read-only inspection of the installed Go1.22.12 `src/os/types_unix.go` confirms that implementation. Do not feed custom FileInfo values or independently obtained pathname-only metadata to this check. Equal contents or source hashes are not file identity; distinct equal-content files remain valid report destinations. Saved IDs are operation-scoped safety evidence, not persistent cross-run document identity.

On Windows, use `GetFileInformationByHandleEx(handle, FileIdInfo, ...)` for input and output handles and compare the full volume serial plus 128-bit FileId. Microsoft specifies this pair for comparing open files. x/sys v0.20.0 already exposes the call and FileIdInfo constant; a minimal local FILE_ID_INFO ABI layout is needed (64-bit volume serial plus 16 identifier bytes), with layout/error tests later. Query/type failures mean safety is unestablished and must fail, not mean "different file." [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info), [pinned constants](https://raw.githubusercontent.com/golang/sys/v0.20.0/windows/types_windows.go).

Do not use Go1.22 Windows SameFile as a universal substitute: its File.Stat identity is a volume serial plus64-bit file index, while path-origin metadata can lazily reopen a pathname and a lookup failure returns false. Microsoft explicitly says64-bit IDs are not guaranteed unique on ReFS and file-ID support varies by filesystem. Source reads inspected here were `src/os/types_windows.go`, `src/os/stat_windows.go` and `src/syscall/syscall_windows.go` beneath the previously recorded installed Go1.22.12 toolchain directory. File.Truncate dispatches through the held Windows handle to SetEndOfFile. These are source/API observations, not executed Windows proof. Require FileIdInfo support or fail filesystem report output; do not silently use a weaker ReFS/path fallback. [Microsoft file-ID limitations](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information).

Withhold FILE_SHARE_DELETE on retained Windows output/root handles as with input acquisition, and retain the required ancestors within the relevant acquisition/write scope. Input handles close after identity capture/read, so this does not block corpus-file deletion for the whole analysis/output duration. Sharing conflicts fail normally. On Unix, replacing or moving the destination name after its handle is checked cannot redirect writes to a newly installed source alias; writes still affect the checked old object, which may no longer be reachable through the original report pathname. This is the accepted held-object boundary, not a guarantee of immutable path ancestry or that a concurrent actor cannot change names/content. Existing-output failure may leave that non-input report partially written, and exclusive creation may leave an empty/partial new report; no transactional output/crash durability is promised. The toolkit never truncates the protected acquired input objects.
