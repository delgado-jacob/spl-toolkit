# Milestone 7 — Developer Tooling and Ecosystem Design

Status: architectural design and complete written spec approved by the delegated controller on 2026-09-07. The verified Milestone 6 handoff remains a prerequisite for a final implementation plan. This document specifies behavior; it does not authorize production changes, version bumps, commits, uploads, publishing or migration writes.

## Purpose and scope

Turn the canonical local engine into practical repository, CI, migration-assessment and editor tools. Users can scan dedicated query files, inspect aggregate dependencies and coverage, export SARIF and graph data, compare schema/mapping changes, and receive local editor diagnostics and field highlights. Go and real native Python remain first-class embedding surfaces; the optional REST adapter stays stateless and thin.

Include a stable useful advanced document view and published versioned machine contracts. Exclude graphical IDE/dashboard development, query execution, live catalogs, autocomplete, automatic bulk migration, arbitrary host-language query extraction, multiple editor extensions and non-SPL language support. The PRD's advanced representation requirement does not require a complete public AST. Temporary `_build_plan/` files never become runtime, test, package or documentation-generation inputs.

## Architecture and chosen approaches

Canonical analysis/validation/rewrite packages retain all language interpretation, field transfer, schema projection and rewrite eligibility. A shared Go corpus layer orchestrates already-normalized documents and composes reports. A separate local loader discovers and reads files. Exporters project canonical evidence into graph/SARIF shapes. An impact component compares canonical before/after results. The LSP process owns protocol/document lifecycle and delegates analysis to the same engine. None implements a parser, field matcher, scope resolver, predicate evaluator or lineage engine.

The controller approved three choices. Explicit dedicated files plus a strict manifest provide practical imports without creating format-specific extraction parsers; files-only would underserve embedding, while arbitrary dashboard/XML/code extraction is too broad. Revision-qualified graph evidence and static before/after impact are useful without a persistent graph database or cross-edit symbol-identity system; status-only impact would hide relevant differences. LSP 3.17 full-text synchronization, diagnostics and document highlights satisfy local editor needs without incremental-edit, semantic-token, autocomplete or extension-distribution scope.

Exact package/API type spellings and the smallest shared helpers are selected after verified M6. Keep these component responsibilities cohesive; do not create one abstraction per output field. Reuse existing batch/report and source utilities without changing earlier atomic batch failure semantics.

## Corpus selection and source contract

A directory scan recursively selects regular files with exact lowercase `.spl` or `.spl2` extensions. Each complete UTF-8 file is one query, with dialect selected by extension, profile `splunkd`, and the supported default compatibility version. Preserve bytes, whitespace, comments, line endings and any BOM for canonical analysis; never trim, strip or repair text in the loader. Whitespace-only content remains a selected document and produces the engine's syntax-invalid report.

Discovery skips directories named `.git`, `.hg`, `.svn`, `.worktrees`, `node_modules`, `vendor`, `.venv`, `venv`, `build` and `dist`. Apply this finite name list at any depth and record it in selection metadata. There is no custom ignore language or implicit `.gitignore` parser; use an explicit manifest for a different selection. Do not traverse symlink entries; record skipped symlinks separately from analyzed files. Unselected extensions and ignored subtrees do not contribute to analyzed counts. An explicitly selected scan root must be a real directory; a symlink root is a request error.

The strict manifest has integer `schema_version: 1`, a `base` path, and nonempty ordered `documents`. `base` is a relative directory resolved against the manifest's parent; omission means `.`. Each document requires nonempty unique `id`, exactly one of literal `text` or query-file `path`, and optional `language`, `profile`, `version` and `source_id` using the canonical QueryDocument meanings. Nulls, wrong types, unknown manifest/entry keys, duplicate IDs, invalid options and text/path conflicts are rejected before analysis. A file entry with no language selects `.spl`/`.spl2` by extension; another extension requires explicit language. Inline entries default to SPL if language is omitted. An explicit manifest dialect can override extension because it is a caller selection rather than guessing.

Manifest query paths are slash-separated relative paths within the declared base; absolute paths, drive/UNC paths, backslashes and parent traversal are rejected as input structure errors. The resolved base itself may be a chosen manifest-relative directory; query entries cannot escape it. Containment is checked before reads and maintained when opening files; do not follow symlink components. Once a structurally valid entry is selected, a symlink, nonregular file or inaccessible path is a per-document acquisition failure, not a silently omitted query. Explicit manifest paths can select files under an ordinarily ignored subtree. A repeated path under distinct explicit IDs is permitted as two intentionally distinct logical documents, for example to compare dialect contracts; duplicate IDs are never silently coalesced.

Directory IDs and default source IDs are slash-normalized paths relative to the scan root; order is lexical by those paths without case folding. Manifest order and explicit IDs are retained. File entries default their source ID to their relative path; inline entries default it to their manifest ID. Explicit source_id is retained as opaque caller metadata and is not interpreted as a filesystem path or URI. The stable corpus document ID is separate from source_id and physical origin. IDs are compared exactly and must be unique in one corpus.

Normalized entries retain origin kind (`file` or `inline`), logical ID, canonical document and original-source hash. File origins retain the actual selected relative path. Inline origins describe a virtual query document; its query-relative ranges do not identify coordinates inside the host JSON string or an original dashboard/code file. This milestone has no host-source mapping/extraction contract. In-memory callers supply normalized documents without triggering filesystem access.

The original-source hash is SHA-256 of exact UTF-8 bytes. A separate analysis revision identity incorporates that hash, normalized language/profile/compatibility version, tool version and report/capability contract identity with an unambiguous canonical encoding. Target/refinement identity accompanies validation contexts and includes prepared target content and selection/options, or a deterministic content hash covering those inputs and supplied local resources. Caller-supplied identity/version labels alone are insufficient: schema content can change while those labels remain unchanged. Graphs must not conflate differently refined reports. IDs are reproducible for identical inputs and context; they are not promised persistent across edits, engine upgrades or contract changes.

## Failures, aggregation and automation outcomes

Reject malformed manifest structure, unsupported document options, invalid shared targets/mappings and empty selection before publishing a corpus report. Existing single/batch APIs keep their established request-error behavior. Once selection is valid, continue independent selected documents after local acquisition failures. Unreadable bytes, invalid UTF-8, nonregular files, symlinks and traversal/read failures appear as stable acquisition-error records with source identity and stage of failure. A directory traversal failure records the affected subtree and makes selection completeness false; it must not masquerade as an empty successful directory. Read each source into an immutable snapshot before analyzing or comparing it. Internal engine failures remain operational failures, never synthetic syntax findings or successful empty reports.

A versioned corpus report contains ordered entries, acquisition failures, selection metadata, normalized analysis/validation mode, aggregate status, execution completeness, coverage counts and dependency summary. Successful entries embed their complete canonical analysis or validation report. Failed entries have an acquisition error and no invented canonical report. Collections encode as arrays, including empty arrays. Failed paths/errors are ordered deterministically; no timestamps, timings or worker completion order participate in canonical comparisons. Parallelism is optional and must preserve output order.

Aggregate content status uses invalid before incomplete before valid. Any analyzed definite error keeps invalid even when other files failed. With no definite errors, an acquisition/selection gap or canonical uncertainty produces incomplete. Valid requires every selected query to complete analysis and, if selected, validation without definite errors or uncertainty. Execution completeness is independent: it is false for acquisition/traversal/internal failures even when content status is already invalid.

Summaries distinguish selected documents, analyzed documents, acquisition failures and traversal failures. Status counts cover analyzed reports only. Syntax, semantic and schema coverage each show complete/incomplete counts and explicit denominators; schema coverage is `not_requested` in analysis-only mode rather than implicitly true. Report unresolved reasons and command/form coverage using canonical capabilities. Skipped ignored entries are selection metadata, not validated documents. Dependency summaries preserve kind, exact normalized name, document IDs and contributing reference IDs; unresolved wildcard/dynamic evidence is not promoted into a concrete dependency name.

CLI writes an available report before returning a content status. Exits are 0 valid, 1 invalid, 3 incomplete and 2 request/I/O/internal failure. Exit 2 takes precedence if selection, acquisition or writing failed, while an emitted report still preserves known invalid findings. Output-file mode does not duplicate report output on stdout. Error handling never overwrites a query source: scan, graph and impact only read sources. Document report size and source limits using the final engine/adapter limits; crossing a limit is explicit failure rather than silent truncation.

## SARIF export

Emit SARIF `version: 2.1.0` with the official schema URI and conform to the approved Errata 01. Each canonical diagnostic becomes a result with stable code as ruleId, appropriate error/warning/note level, message, original location and coverage/context properties. Use a deterministic rule table with valid indices. Preserve incomplete diagnostics even when no definite errors exist. If canonical uncertainty exists without a located diagnostic, include an explicitly unlocated tooling completeness result explaining that gap; never invent a source range. Do not claim SARIF status alone conveys all independent coverage dimensions.

Set `columnKind: unicodeCodePoints` and convert canonical one-based half-open positions into SARIF regions deliberately. Do not write byte offsets into character-offset fields; omit unnecessary charOffset/charLength rather than use the wrong units. Validate zero-length/end-of-file, multiline and CRLF ranges against SARIF constraints. File artifact URIs use slash-separated relative paths with each segment correctly percent-encoded, a consistent root base ID and an absolute file-URI root mapping with trailing slash. Do not treat a Windows path, `#`, `%`, spaces or Unicode text as an already-encoded URI. Artifact references and region bounds must point to the selected source snapshot.

Inline documents use clearly virtual artifact URIs derived from logical identity and include original text as artifact contents. They do not pretend to locate an escaped JSON string in the manifest. Retain opaque source_id in properties, distinct from artifact identity. Stable document/revision evidence can be exported in properties; no cross-edit fingerprint guarantee is introduced.

Acquisition and tool failures become invocation notifications with `executionSuccessful: false`; available query findings remain in results. A successfully executed analysis with invalid or incomplete queries may have a nonzero content exit and `executionSuccessful: true`. Do not equate exit 1 or 3 with process failure. Invalid input rejected before any report remains a CLI error, not fabricated valid SARIF. Published acceptance examples explain consumer limitations for virtual artifacts and coverage properties.

Validate every representative export offline against a vendored reviewed official SARIF schema, then assert rule/index references, URI encoding, source slices, region units, invocation state and preservation of uncertainty. The normative choices follow the [OASIS standard and errata](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html); protocol provenance is recorded in research-notes.md.

## Dependency and lineage graph data

Export a versioned JSON graph with document, dependency, scope/stage, reference and lineage-transition evidence as needed to reconstruct the canonical relations. Edges state their relation and point back to report/document/reference/transition evidence. Shared exact dependencies can be grouped by kind and normalized name, but that grouping is a static dependency name, not a verified live resource identity. Field references with the same spelling remain separate across scopes, revisions and binding origins.

Document IDs are corpus-stable; stage/reference IDs are namespaced by analysis revision and document ID. Transition identity includes its canonical owner and ordered occurrence/phase rather than assuming stage ID alone is unique. Graph IDs use an unambiguous encoding with documented collision handling, not concatenated unescaped names or source spans. Every node/edge ID is unique and every endpoint resolves. Source ranges remain evidence attributes, not persistent identity.

Preserve canonical conditionality, uncertainty, partial wildcard membership, independent coverage and SQL lineage phase/evaluation order. Stages may be in lexical order while their positions describe logical flow; exporters must read explicit phase/order evidence rather than infer it from array order or source locations. Never fabricate a complete edge for an unmodeled merge or dynamic reference. Partial graph data is useful and remains explicitly partial.

## Schema and mapping change impact

Schema impact snapshots one corpus once, then validates the identical documents against explicit before and after local targets through the existing field-list/JSON Schema/OCSF operations. A comparison can use different supported target kinds if the caller selected them explicitly. Prepare each target once; invalid target structure rejects the request. Mapping impact runs M6 previews for explicit before/after mapping requests against those unchanged original snapshots. An empty mapping side represents an explicit identity baseline. Preserve complete rewrite audits, candidate documents, post-analysis and requested validation for each side; no source files are changed.

Each document result shows before/after status and coverage, changes in dependency evidence, field outcomes and diagnostics, and applied/skipped/ambiguous rewrite groups where applicable. Include introduced/resolved/changed findings even when coarse status remains invalid or incomplete. Report a static affected/unchanged/indeterminate classification with reasons. Unchanged is reserved for equal compared canonical evidence with complete comparison coverage; equal incomplete reports remain indeterminate about unobserved impact. A new validation error is an observed static regression; disappearance of an error is not proof of runtime-equivalent behavior.

Align unchanged source references by source revision and exact canonical identity, verifying kind/role/scope/range evidence. If refinement affects identifiers, use an exact unique original-evidence match and expose ambiguity rather than pairing by array position. Diagnostic deltas pair stable code/category and associated unique reference evidence, retaining message/severity/coverage changes; duplicate unresolved associations remain unmatched/ambiguous. Mapping candidate alignment uses M6's original-reference/edit-group provenance and any verified post-source alignment. If M6 cannot prove a relation, show candidate evidence separately. Do not derive persistent identity from shifted spans, same spelling, nearest location or a guessed whole-query correspondence.

Summary counts include affected, unchanged, indeterminate and failed documents and concrete introduced/resolved/changed finding totals with explicit denominators. Input/acquisition failures remain visible and prevent a complete impact assessment. The before/after selection itself is caller intent: the toolkit neither selects a target schema from query predicates nor claims search execution, migration safety or runtime equivalence.

## Stable advanced document view

Expose the smallest useful detached document API over canonical source, scopes, stages, references, lineage, dependencies, diagnostics and coverage. Include revision identity and any already-public M6 eligibility/audit facts through their existing contracts. Do not expose generated parser types, token streams, mutable contexts, or internal predicate implementation. No second public AST or semantic evaluation engine is required.

Consumers can enumerate typed evidence, look up a scope/stage/reference by ID, retrieve exact original text for a checked range, find references intersecting a range, and trace existing origin/transition relationships. Unknown IDs return an explicit not-found result; invalid ranges are errors rather than clipped source slices. Range intersection uses half-open intervals; a position query contains a nonempty reference when start <= position < end. Overlapping matches return all matches in canonical reference order, not an arbitrary winner. Zero-length references match only an explicit exact-position lookup, and position at document EOF does not attach to the preceding reference by default.

The view is a caller-owned deep-detached value: callers may mutate their copy, but cannot mutate engine state, another result or global capabilities. Helpers derive lookup results from the provided snapshot and cannot return stale cached indices after caller mutation. Mutating evidence does not produce a new engine-verified analysis or preserve its revision attestation. Explain that ID equality is only meaningful under the same document/revision context. Document lexical source order separately from logical stage position and phase evaluation order.

## Local language server

Provide `spl-toolkit lsp --stdio` implementing the chosen LSP 3.17 feature baseline. The official project now advertises a later protocol version; this is a deliberate compatibility target, not a latest-version/full-feature claim. Implement initialize/initialized, full-text document open/change/close, configuration changes for supported local targets, push diagnostics, documentHighlight, cancellation and shutdown/exit. Advertise only these implemented capabilities. Stdout contains framed JSON-RPC traffic only; process logs go to stderr. Unknown requests receive protocol method errors; notifications and lifecycle violations follow the protocol rather than producing corrupt stdout.

Select dialect explicitly from didOpen languageId `spl` or `spl2`. Profile/version come from supported initialization/configuration options, with canonical defaults. Unsupported language IDs/options and invalid local-target configuration are service configuration errors, not invented syntax errors at line one. Schema configuration is optional; a bad requested target must not silently fall back to an apparently complete analysis-only service. Prepare local target snapshots using the same decoders. No network/schema retrieval occurs. Configuration changes invalidate validation snapshots and reschedule affected open documents.

Open-buffer text is authoritative and is never replaced from disk. Key state by document URI, open generation, monotonically advancing client document version and configuration revision. Full-sync didChange replaces the full snapshot; invalid incremental changes under the advertised full-sync contract are explicitly diagnosed at the protocol/service boundary. Reject stale/duplicate versions without altering current text. Closing clears diagnostics and disposes the open generation; reopening at a reset version cannot admit old results.

Use bounded/coalesced background analysis rather than one unbounded goroutine per keystroke. Cancel superseded work where supported and always suppress obsolete diagnostic publication by checking URI/generation/version/configuration at publication time. Do not promise forced cancellation of ANTLR if the verified engine cannot provide it. Publish every complete replacement set, including empty diagnostics to clear prior findings. Include the analyzed version when the client supports it and suppress stale publication even when it does not.

Select UTF-16 position encoding and convert from exact engine byte offsets using the same source snapshot. LSP lines/characters are zero-based; engine columns are one-based Unicode code points and cannot be converted by subtraction alone. Respect LSP line-ending conventions including CRLF and lone CR in the adapter's offset map. Positions inside non-BMP characters require surrogate-pair accounting. Incoming positions are resolved against the captured snapshot with protocol-specified line-end behavior; invalid offsets must not slice inside UTF-8 bytes. [Microsoft's position contract](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/types/position.md) defines these units.

Document highlights use canonical binding and origin evidence to select related reads/writes. Same spelling in independent scopes or before/after unrelated assignments does not imply one symbol. Unsupported/ambiguous bindings return only defensible selected evidence or no highlights; do not perform fuzzy text matching. Classify reads/writes from canonical roles/binding, using Text only when appropriate. If overlapping references at a cursor cannot be uniquely resolved, return no invented binding group.

A position-based request captures its document snapshot in message order and receives a response even if diagnostics later become stale. Honored client cancellation returns RequestCancelled; never silently discard a request. Ordinary queued text edits alone do not justify ContentModified; internal configuration invalidation may do so where permitted by the protocol. Keep asynchronous diagnostic suppression separate from request completion. On shutdown, stop scheduling, complete/cancel outstanding requests according to protocol, and exit with the lifecycle-prescribed status.

## Public adapters and machine contracts

Canonical Go exposes in-memory corpus scanning/aggregation, SARIF/graph projection, schema/mapping impact and advanced document access. The shared local loader is usable without giving server code implicit file access. CLI adds `scan` with text/json/sarif output, `graph` with JSON, `impact-schema` and `impact-mapping` with text/json, and the LSP command. Corpus commands accept exactly one directory or manifest selection, reuse explicit target and output conventions, and reject conflicting options. Individual analysis/validation/rewrite commands remain available.

Native Python exposes the document-based corpus, export, impact and advanced-document operations through the existing owned native result boundary. Canonical reports are dictionaries; SARIF is a canonical SARIF object that callers may encode normally. Preserve operation guards, closed-handle errors and finally-based native freeing. Python file users can read dedicated files normally or construct the documented manifest; do not replace native semantics with CLI subprocess calls. Keep C exports/native headers and explicit package source lists complete.

The optional REST surface exposes equivalent in-memory operations using inline documents/targets and direct canonical reports; it accepts no server filesystem paths or remote retrieval URLs. Apply existing transport size limits and distinguish malformed requests from content statuses. No LSP-over-HTTP or persistent workspace service is introduced. Select exact route/method names after M6 so they follow existing conventions, and document every exposed operation rather than leaving parity ambiguous.

Publish versioned standalone machine-contract JSON Schemas outside `_build_plan/`, sharing definitions across QueryDocument, analysis, capability, validation, rewrite, corpus, graph, impact and advanced-view families. Keep existing successful wire shapes compatible. New report families start at integer schema_version 1; schema family identity is part of the named contract, not inferred from the integer alone. Canonical/new request decoders are strict. Do not retrofit breaking strictness onto legacy endpoints without a separate compatibility decision. Output consumers tolerate unknown additive properties within a known version; required-property removals, changed meanings/types and additions to a documented closed enum require a new contract version. Document open extension points explicitly instead of assuming all enum additions are compatible.

Use a full standards-conforming JSON Schema instance validator for wire-contract tests. M4's field-projection validator is not an instance validator and must not be repurposed as proof of schema conformance. Validate positive and negative request/report fixtures, preserve old-version fixtures and test actual emitted JSON. Publish diagnostic code/severity/category explanations, capability form limitations, source-unit/identity semantics, status precedence and compatibility/version policy alongside schemas. Runtime loading of remote schema IDs is unnecessary; vendored schema validation remains offline.

## Release, embedding and acceptance

Extend the existing release/package machinery rather than add an unrelated pipeline. Explicit artifact manifests include CLI/LSP executable, native library/header, genuine native Python wheel and source distribution, machine schemas, capability/diagnostic documentation, licenses/notices and runnable examples. Include all required native sources and both grammar frontends. Examples cover Go embedding, real Python corpus/impact use, CLI scanning and SARIF CI consumption, graph import, and one compatible local editor configuration without distributing an extension.

Preserve the Go 1.22 language floor, verified supported platform set and source-derived version agreement from M6. Choose loader/protocol/package dependencies and APIs compatible with those contracts. Any claimed filesystem containment or no-symlink guarantee needs concrete implementation tests on the supported path/open behavior; lexical path checks alone do not prove it. A version bump, new platform or remote upload is not implied by this design. Check installed artifacts outside the checkout so missing package data or accidental source-tree imports cannot pass. Exercise the packaged CLI's LSP startup/handshake and real native Python operations, including close/concurrency behavior. Existing clean-build, release reproducibility and exact-source acceptance tools remain the foundation. Configured or historically successful remote jobs are not current-head acceptance; record precisely which platform/toolchain jobs actually ran.

Required automated acceptance includes:

- Dedicated and manifest corpora with mixed dialects/statuses, stable ordering/IDs, byte preservation, empty selection, duplicate IDs, containment violations, ignored subtrees, symlink/nonregular/unreadable/non-UTF8 acquisition errors, directory traversal failures and output write failures.
- Aggregate denominator/status/coverage correctness, retained findings after independent failures, source hashes and context-sensitive revision identity, repeated/concurrent determinism and unchanged existing batch atomicity.
- Graph uniqueness, endpoint/report-pointer integrity, conditional/unknown lineage, repeated names in distinct scopes, SQL lexical versus phase order and no stable-ID claims across revisions.
- Schema/mapping comparisons with identical sources, explicit identity baselines, introduced/resolved/changed findings despite unchanged status, ambiguous alignment, partial previews, candidate-validation differences and proof that no input files are written.
- SARIF official-schema validation plus semantic URI/rule/index/region/invocation assertions for Unicode/non-BMP/CRLF, path spaces/#/%/Windows cases, virtual artifacts, no-findings, invalid-plus-incomplete and operational failures.
- LSP framing/lifecycle, full synchronization, Unicode position conversion, diagnostics replacement/clear, rapid version/configuration races, close/reopen, cancellation responses, highlight snapshot order, unrelated same-spelling bindings, unsupported language/configuration and clean shutdown.
- Full canonical report equivalence across Go, CLI, actual native Python and exposed REST operations, with normalization limited to object-key order. All new request/report families validate against their published schemas, and old reports remain compatible.

Run the established relevant Go race, native Python, package/source/build and parser reproducibility checks against the actual implementation. Protocol harness/schema tests establish automated correctness; additionally run a reproducible local compatible editor LSP client and local standards-based SARIF consumer integration. Those integrations require neither a user account nor remote upload. Record commands, client/consumer versions, observed findings and source SHA. Unrun manual/editor or cross-platform gates remain explicitly open; screenshots or green schema validation cannot substitute for actual client behavior.
