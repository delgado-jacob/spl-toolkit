# Milestone 5 — Broad Standalone SPL2 Support

Status: architectural design and complete written spec approved by the delegated controller on 2026-09-07. It deliberately leaves exact internal transfer and additive SQL phase field/type names to the verified Milestone 4 handoff. No production changes, implementation plan, workers, or commits are authorized by this document alone. Planning and development require that handoff and controller direction.

## Purpose and boundaries

Make explicit standalone SPL2 input a first-class consumer of the canonical analysis and schema-validation system. Cover pipeline and SQL-style searches for the documented `splunkd` contract while preserving established SPL behavior. Expose source-aware dependencies, references, stages, scopes, lineage, coverage and diagnostics through Go, CLI, native Python and optional REST. Grammar acceptance and semantic understanding remain separately visible.

The input is one standalone search. Imports, exports, module namespaces, named module searches, reusable function/command/type declarations, multiple module statements and non-splunkd profiles are excluded. No query execution, remote dependency resolution, account, live server, transpilation, new mapping engine or developer-tooling service is introduced. `_build_plan/` stays temporary guidance; production conformance data and documentation belong outside it.

The controller acts as the delegated design approver under the user's autonomous milestone workflow. The authoritative research and conflict rulings are recorded in [research-notes.md](research-notes.md), retrieved 2026-09-07.

## Approved architecture

Add a dedicated Go-generated SPL2 ANTLR lexer/parser frontend. The frontend owns SPL2 tokenization, grammatical structure, syntax diagnostics, identifier/literal distinction, expression roles, dialect-specific command forms and lowering to the canonical semantic kernel. Typed parse-tree contexts drive lowering; no regex, string splitting, token-text guessing or rewritten SPL query substitutes for a parser.

Both SPL and SPL2 feed the same command-transfer, binding, lineage, source-universe refinement and validation behavior. A shared operation accepts frontend-resolved semantic facts, such as assignment sequencing, projection policy, output names and source spans. It must not impose SPL spellings or defaults on SPL2. The actual internal interface and smallest necessary extraction from the finished SPL frontend are selected only against verified M4. Do not create a second SPL2 flow engine or adapter-side field matching.

The existing SPL lexer uses case-insensitive matching and permissive SPL forms, with an immutable per-input analysis CharStream marker for narrow dot disambiguation. Preserve that behavior and its isolation guarantees. SPL2 lexical requirements are sufficiently different that extending this marker into a pervasive dialect mode is rejected. A separate full analysis engine is also rejected because it would duplicate field-flow and schema decisions.

All mutable parser and lowering state is local to one call. Preserve source bytes, UTF-8 byte offsets, Unicode columns, CRLF handling, deterministic IDs, stable ordering and copied public capabilities. Public types never expose generated contexts. Syntax recovery retains intact typed contexts while withholding findings that depend on inserted or damaged nodes. Synchronize using lexed delimiters and grammar boundaries, never by splitting original text at pipes.

## Approved standalone contract

`QueryDocument.language` accepts `spl` and `spl2`; omitted/empty language remains SPL. Profile remains `splunkd`, version remains `current`, and source identity remains caller metadata. Unknown nonempty language/profile/version values are request errors. `current` means the capability contract published by this build, with its documentation snapshot identity, not a guarantee about any unspecified Splunk server release.

SPL2 supports explicit `search`, `FROM`, `SELECT ... FROM`, supported generating commands, and the documented omitted-search form beginning with `index=<name>`. For example, `index=main error` is allowed; `404 index=main` is not; `search 404 index=main` is allowed. No generalized missing-command recovery or automatic SPL/SPL2 guessing is introduced. This follows the July 2026 standalone manual rather than importing module-only initial-search requirements.

## Approved measurable syntax coverage

The researched matrix contains 25 language families: starts; identifiers; literals; comments; search predicates; expression precedence; conditional predicates; arrays/objects; access paths; templates; inline lambdas; projection/rename lists; aggregation/window forms; lookup lists; FROM-first SQL; SELECT-first SQL; SQL followed by pipes; dataset literals; SQL joins; pipeline joins/subsearches; union; metrics/data models; extraction/options; embedded SPL; conditional paths. Every family must have reviewed positive and negative fixtures and documented semantic expectations.

The minimum native command inventory with dedicated form-aware rules is: search, from/select, eval, where, fields, table, rename, stats, eventstats, streamstats, lookup, sort, dedup, head, reverse, join, append, appendpipe, appendcols, union, if, spl1, bin, rex, spath, makeresults, loadjob, tstats, mstats, timechart, timewrap, makemv, mvexpand, mvcombine and fillnull. This is 35 command families, counting from/select together. A manifest row also accounts for every command in the current authoritative splunkd compatibility inventory, including deferred/unimplemented forms. Unsupported profile entries are explicitly identified.

Before production implementation, convert these families into an exact command/form matrix against individual official syntax references. Each advertised form has at least two independent positive cases and two minimal malformed variants; a zero-argument command can use illegal trailing operands or options as negative cases. Require at least 200 distinct labeled fixtures overall, at least 80 negative/malformed/profile cases, and at least 40 FROM-first, SELECT-first and mixed SQL/pipeline cases. These floors supplement coverage review: duplicated spelling/case variants do not establish a new form. Report actual counts and uncovered inventory entries in the handoff.

Supported command rules enforce required operands, delimiters, list commas, permitted option placement and clause dependencies even when field semantics are unmodeled. No permissive opaque alternative can accept a malformed supported command. For unimplemented command grammar, do not advertise syntax support merely because its name and balanced tokens were retained for recovery. The manifest distinguishes native profile membership, recognized command forms and modeled field effects.

Lexical and expression fixtures include quoted reserved and Unicode identifiers, strings versus raw strings, comments containing pipes, source spans after multibyte text, Boolean/null spellings, arrays versus subqueries, object keys versus reads, navigation versus dotted identifiers, template delimiters, search literals versus embedded SPL backticks, and function versus command contexts. Cover operator precedence and unary operators structurally, not just the set of discovered fields. SPL2 uses `+` for concatenation; dot is navigation rather than the legacy SPL concatenation operator.

SQL fixtures enforce both clause hierarchies, required FROM, GROUP BY/SELECT dependencies, list delimiters, supported keyword casing, SELECT DISTINCT, HAVING, ORDER BY/ORDERBY, GROUP BY/GROUPBY, LIMIT/OFFSET, aliases and INNER/LEFT joins. Unsupported RIGHT/FULL joins and malformed supported forms cannot silently fall through into unknown arguments. Lowercase and uppercase keyword forms are supported as documented; arbitrary mixed-case acceptance cannot be inherited from the SPL lexer.

## Approved core semantic coverage

The fully modeled command set is search, where, eval, exact rename, fields, table, stats, eventstats, streamstats, lookup, sort, dedup, supported head and reverse forms, plus plain dataset FROM and supported SQL clauses. It uses the scalar and aggregate function semantics verified by M2 with SPL2-specific grammar, arity, profile membership and result naming. The required ordinary scalar family is abs, round, ceil/ceiling, floor, len, lower, upper, trim/ltrim/rtrim, substr, replace, coalesce, if, case, isnull/isnotnull, tonumber, tostring, mvcount, split and match. The core aggregate family is count, sum, avg, min, max, values, list, dc/distinct_count, first and last. Each needs documented arity/form restrictions and a splunkd compatibility check; the manifest never assigns unconditional semantic support to every argument form. Full support means complete field effects, not evaluation of field values or successful search execution. Any unsupported option/form/function makes the affected stage incomplete.

Ordinary search RHS values are literals; expression identifiers on either side are reads. Dependency selectors are recognized only in grammar-established source-selector positions. In SQL WHERE, fields such as sourcetype remain actual expression reads; dataset names from FROM are dataset dependencies, with no guessed index/lookup kind merely from spelling. Value predicates do not select schemas or resolve joins.

Eval assignments operate left to right. Exact null assignment removes the field, rather than creating a definitely present null-valued field. Scalar functions that might return null do not justify stronger availability claims than the kernel can prove. Boolean eval assignments are admitted under the controller's 2026-09-07 ruling using newer concrete true/false examples; the older contrary eval sentence is a recorded source conflict. For rename, the newer command-specific usage restriction supersedes the older sequential examples: repeated sources, repeated targets, chains and overlapping/circular pairs are located definite-invalid contract findings. Ordinary independent exact pairs remain complete. Do not add a sequencing abstraction solely for contradicted forms; choose the smallest shared-kernel policy after verified M4. Other unproven forms remain incomplete.

Fields inclusion preserves the documented `_raw` and `_time` defaults unless explicitly removed; table and SQL SELECT have their own projection rules. Do not invent source-required references at zero-length spans for implicit internal fields. Their availability is an engine policy, not evidence that a supplied external schema declares them. Finite/partial source-universe wildcard refinement remains the single canonical implementation introduced by M3/M4.

Stats closes output to grouping keys and aggregations; eventstats/streamstats preserve input fields while adding supported outputs. Alias-free native `count()` produces `count`, supported field aggregates preserve the tested name such as `sum(bytes)` or `dc(action)`, and explicit AS wins. Frontends resolve these names before shared transfer. A complex implicit expression label whose spelling cannot be proven stays incomplete; never guess by applying a generic SPL string formatter. Official standalone FROM examples use `count()` followed by HAVING/ORDER BY over `count`, and standalone examples explicitly name `sum(bytes)` and `dc(action)` outputs. The research notes record independent corroboration from an expanded native search body in the custom-command documentation; its module wrapper is not admitted.

Plain external datasets, including quoted names, begin with the kernel's open source state. Resource/namespace-qualified dataset forms beyond those explicitly admitted by the reviewed matrix remain unsupported syntax/incomplete, not a guessed ordinary name or a claim of globally invalid SPL2. Actual excluded module declarations receive the separate module error below. Dataset literals with statically known object keys produce local fields and no external input obligations; fields missing from some rows are conditional. Dynamic dataset functions are incomplete unless specifically modeled. Static nested object navigation can use schema path evidence only when the finished M4 representation preserves its distinction from a literal dotted field or dataset alias. Dynamic keys/indexes and unsupported array traversal preserve base/index reads and yield indeterminate outcomes.

Joins, union and if/append branch merges may remain incomplete while showing trustworthy child scopes, dependencies, predicate reads and local lineage. Child scope inheritance follows the command: independent source subqueries do not inherit parent fields; subpipes/conditional branches inherit a copied parent environment. Unmodeled merges cannot leak child-created names as proven parent output. Qualified alias reads must not become fabricated root field names such as `L.id`; preserve their role/scope or mark the binding indeterminate.

Inline lambdas are expression syntax, distinct from reusable declarations. Parse parameters and bodies through ANTLR; local parameters/variables are not event fields. Lambda semantics, field templates, dynamic indexing, embedded spl1, unimplemented extraction, metrics and other unknown effects stay incomplete with specific limitations. Preserve ordinary reads inside typed template expressions, but do not convert computed names into exact references. Unknown function calls never default to a complete pure-function handler. A profile-incompatible function is explicitly diagnosed.

## SQL stage and lineage order

Preserve stages and stage IDs in lexical source order, and reference IDs/locations in the original source contract. Assign existing stage `position` by logical clause-entry order within each scope; emit lineage in actual evaluation order. For `SELECT host FROM main WHERE bytes>0`, lexical stages are SELECT/FROM/WHERE, positions are 2/0/1, and field flow is FROM, WHERE, SELECT. A clause can have later internal finalization as described below. No public parser detail or source rewrite is required. Documentation must state that callers use position for clause-entry flow rather than assuming textual SQL order is execution order.

FROM establishes the input environment. WHERE reads that environment. GROUP BY records grouping reads without deleting fields needed by aggregate arguments. Internal processing retains separate pre-group input, aggregate/group/alias, and selected-output environments. SELECT expressions own their original aggregate/output references; aggregate calculation does not immediately erase grouping evidence. HAVING and ORDER BY resolve against the appropriate supported postaggregate environment. Final output projection is applied at the SQL boundary before the next piped command. LIMIT/OFFSET do not create fields. A SELECT alias must not suppress a same-named source requirement in the earlier WHERE clause.

Official examples establish HAVING reads of selected aggregate aliases and implicit `count`. They do not conclusively establish HAVING visibility of a grouping key omitted from SELECT. For `SELECT sum(bytes) AS total FROM main GROUP BY host HAVING host="a"`, preserve the known grouping requirement for host, make the HAVING binding indeterminate with a specific visibility limitation, and return incomplete rather than a fabricated unavailable-field error. Use the same conservative rule for unproven visibility of unselected aggregate expressions or ORDER BY inputs. Single-quoted `'a'` would be a field identifier, not the intended string literal.

No synthetic source stage may stand in for an internal evaluation phase. Final projection remains SELECT-owned through original SELECT lineage/reference evidence, even though evaluation includes later HAVING/ORDER BY clauses. Repeated SELECT-owned aggregate/projection lineage entries must include explicit phase and execution-order metadata, with coherent before/after states for the actual phase order. Bare duplicate stage IDs without this explanation are insufficient. Select exact additive field/type names against the verified M4 lineage contract before final planning. Preserve existing SPL wire output where phases are unnecessary. Never attribute final projection to HAVING or fabricate a source span for a made-up pipeline command.

Support no-join SQL queries with plain field projections, explicit expression aliases, SELECT DISTINCT, supported aggregates, exact grouping keys, supported post-projection predicates/order, and integer limits. Grouped aggregate arguments read the original pre-projection environment. Unsupported grouping expressions, uncertain implicit labels, alias collisions, mixed aggregate/non-grouped expressions or unresolved alias visibility must produce an explicit semantic limitation or a proven invalid diagnostic as appropriate; they cannot be declared valid through permissive lowering. Tests pair equivalent FROM-first/SELECT-first/native pipeline results while comparing source locations only against their respective original texts.

## Diagnostics and adapter behavior

Use existing status precedence: a definite syntax/field/contract error makes invalid, retaining incomplete coverage; otherwise unresolved syntax or semantics makes incomplete. Valid is complete, error-free static analysis. Recovery must retain valid adjacent stages without upgrading the malformed region. No network or runtime acceptance claim is made.

Distinguish three boundaries: malformed supported syntax is an error; well-formed supported-profile syntax with unmodeled effects is incomplete; expressly excluded module/profile constructs are rejected with a located explanation naming the selected standalone contract. Stable codes are `SPL_UNSUPPORTED_MODULE` (error, unsupported_syntax) for excluded module/declaration/multi-statement input and `SPL_PROFILE_MISMATCH` (error, compatibility) for a known construct unavailable in the selected splunkd profile. Such results are invalid for the chosen contract, retain other findings and report syntax/semantic coverage as false; the message must not imply the feature is malformed in every Splunk product. Unknown/unimplemented standalone grammar produces incomplete syntax coverage rather than claiming grammar acceptance. Unsupported document options remain request errors rather than query findings. Do not overload unknown-field errors for unsupported language features.

Go analysis and every single/batch field-list, JSON Schema and OCSF validation operation accept Query Documents with either selected dialect. CLI passes its existing language/profile/version flags without guessing. Batch documents select their own dialect; global conflicting batch flags remain invalid requests. Native Python forwards document options through the existing owned-result/operation guard and frees results in finally. REST accepts the same options in canonical documents and remains a thin adapter. Existing default SPL clients and legacy behavior stay compatible.

Original text-only Go methods and old C ABI exports remain expressly fixed-SPL; they have no dialect parameter and perform no byte-based guessing. The new document-based analysis/validation APIs are the canonical SPL2 path. Legacy CLI discover/map/validate operations expose selectors and reject explicit SPL2 with a request error `unsupported_dialect_for_operation`, pointing to analysis/structured validation or the later M6 rewrite operation as appropriate. Python legacy discovery/mapping methods accept keyword selectors with existing SPL defaults and reject explicit SPL2 consistently; legacy REST request structs recognize dialect fields and reject unsupported selection instead of silently ignoring it. No Go facade is added solely to reject a dialect: existing fixed-SPL methods plus canonical document APIs suffice. Never project an incomplete canonical report into a success-shaped flat discovery result.

Capability discovery supports explicit dialect selection across Go, CLI, Python and REST while preserving no-argument/default SPL behavior. Each language/profile contract reports the documentation snapshot, accepted syntax/form limitations, complete field-semantic forms and function support separately. Its data is static local build data and safe to mutate only on caller-owned copies. Query results retain their normalized selected document. No adapter invents dialect metadata or maintains its own semantic capability table.
