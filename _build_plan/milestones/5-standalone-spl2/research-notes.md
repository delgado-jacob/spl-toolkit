# Standalone SPL2 conformance research

Research date: 2026-09-07. This is design evidence, not a claim that the current parser implements these forms. All sources below are official Splunk documentation retrieved on that date. Source update dates are documentation metadata, not a server compatibility guarantee. No Splunk execution oracle was used. The eventual offline corpus must retain source URLs, retrieval dates, construct/form labels, expected syntax outcome, expected semantic coverage, and exact source-span assertions in durable test data outside `_build_plan/`.

## Authority and context ruling

The controller approved targeting the documented **standalone Search & Reporting forms in the splunkd profile**, including the specific initial implicit-search case. [Start searching using SPL2](https://help.splunk.com/en/splunk-enterprise/search/spl2-search-manual/getting-started/quick-start-write-and-run-a-basic-spl2-search/start-searching-data-using-spl2) (updated 2026-07-27) permits omitted `search` when the first expression is `index=<name>`, and explicitly rejects the equivalent omission before a keyword. Thus `index=main error` is a positive fixture; `404 index=main` is a negative fixture; `search 404 index=main` is positive. This does not authorize arbitrary command inference or dialect guessing.

The [search command reference](https://help.splunk.com/en/splunk-enterprise/search/spl2-search-reference/search-command/search-command-overview-and-syntax) (updated 2026-06-16) still describes `search` as required. The standalone-specific manual governs this context. Named module searches, imports, exports, namespaces, declarations and reusable custom functions remain excluded by the PRD. The [searching overview](https://help.splunk.com/en/splunk-enterprise/search/spl2-search-manual/getting-started/searching-data-using-spl2) (updated 2026-07-27) distinguishes the single-search bar from module functionality.

Resolve other conflicting examples by the applicable standalone context, then command-specific syntax/usage, then worked examples. Preserve a conflict note instead of blindly importing an example into positive fixtures. In particular, the generic syntax introduction contains example clauses/quotes inconsistent with specific command rules; head examples disagree about argument placement; some FROM examples elide WHERE with explanatory ellipses. These are not authority to accept malformed supported syntax. Ambiguous additional forms require further primary-source evidence or a recorded unsupported limitation.

## Architecture evidence and handoff boundaries

The current SPL grammar uses case-insensitive lexing, optional list commas, SPL identifier boundaries, a typed analysis entry rule, and the immutable per-input analysis CharStream marker. It cannot safely become SPL2 merely by selecting the same entry point and changing a language label. Dedicated SPL2 lexer/parser rules with shared semantic lowering are recommended; no production API or refactor has been authorized by these notes.

The design records the approved command-family minimum, measured corpus breadth, inline lambda/embedded SPL limitations, qualified dataset limitation and SQL field-transfer subset. Before implementation, finalize the exact per-command form matrix and path-representation compatibility against verified Milestone 4. Exact source spans, literal dotted identifiers versus object paths, dataset-qualified names, implicit internal fields, and null-removal behavior require particular scrutiny. A parsed unknown-effect operation must not gain completeness merely because all its referenced field names match a schema.

## Follow-up semantic evidence

The controller approved the dedicated frontend/shared lowering architecture and the measured breadth/core scope on 2026-09-07. The 35-command and 200-fixture floors in the design supplement form-matrix quality; they do not substitute for it.

The [standalone FROM examples](https://help.splunk.com/en/splunk-enterprise/search/spl2-search-reference/from-command/from-command-examples), updated 2026-01-16, directly show `count()` later consumed as `count` in HAVING and ORDER BY. They also show GROUP BY host with only an aggregate selected, and HAVING referencing a selected aggregate alias. The [custom-command documentation](https://help.splunk.com/en/splunk-enterprise/search/spl2-search-manual/functions/custom-command-functions), updated 2026-07-27, independently shows its expanded native search body using `stats count()` then `sort -count`. This evidence supports count() producing count without admitting module declarations. The controller approved count(), sum(bytes), dc(action) lowering to count, sum(bytes), dc(action), respectively. Complex uncertain labels need explicit aliases or incomplete coverage.

No retrieved source conclusively establishes whether a HAVING expression may read a GROUP BY field omitted from SELECT, or all aggregate expressions omitted from SELECT. The design must retain separate aggregate/group and selected-output environments, avoid a false unavailable-field proof from premature projection, and classify unresolved visibility as incomplete. Do not import generic SQL behavior as a Splunk fact. Selected alias visibility is evidenced; hidden-key visibility remains a documented boundary. The original example used for this check must spell the string value with double quotes: `SELECT sum(bytes) AS total FROM main GROUP BY host HAVING host="a"`; `'a'` is an identifier in SPL2.

[Rename examples](https://help.splunk.com/en/splunk-enterprise/search/spl2-search-reference/rename-command/rename-command-examples), updated 2026-06-16, explicitly describe left-to-right processing. This differs from the M2 SPL simultaneous-source rename policy and must be an explicit lowering policy. [String templates](https://help.splunk.com/en/splunk-cloud-platform/search/spl2-search-manual/expressions-and-predicates/string-templates-in-expressions), updated 2026-07-27, demonstrate embedded ordinary field/function expressions, so their reads cannot be lost by lexing the entire string as inert text. Expression documentation identifies `+` as the concatenation operator and exact null assignment as field removal.

Some command-specific text itself conflicts with the general rules. For example, the [table reference](https://help.splunk.com/en/splunk-enterprise/search/spl2-search-reference/table-command/table-command-overview-syntax-and-usage), updated 2026-06-16, illustrates a double-quoted wildcard despite the general single-quoted identifier rule. Track that individual form explicitly rather than applying one blanket quote policy. [Into](https://help.splunk.com/en/splunk-enterprise/search/spl2-search-reference/into-command/into-command-overview-syntax-and-usage), updated 2026-06-22, is legal in native searches for supported sinks; it must not be called a wrong-profile command just because streaming examples also use it. It may be unimplemented in this milestone with honest syntax/semantic coverage.

The controller approved conservative hidden HAVING/ORDER visibility and real lexical clause stages with logical clause-entry positions. Repeated SELECT-owned aggregate/projection lineage entries require explicit phase and execution-order metadata with coherent before/after states; projection stays SELECT-owned. Exact additive names wait for verified M4, and existing SPL output is unchanged when phases are unnecessary. The controller also approved invalid `SPL_UNSUPPORTED_MODULE`/`SPL_PROFILE_MISMATCH` results for the selected toolkit contract, incomplete unknown standalone syntax, and explicit SPL2 rejection on legacy operations. Fixed-SPL Go methods plus canonical document APIs are sufficient; no rejection-only Go facade is required.
